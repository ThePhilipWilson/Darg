# Darg

Philip's one app for everything: per-project boards, notes, docs, code, agents, consoles and tools. Native Avalonia (C#, .NET 10), one codebase for Windows, Mac and mobile. The plan and decisions live in `docs/` (PLAN.md, the mockup, MORNING.md, PHONE-PLAN.md), which is the Docs section for this project; they moved there from the Obsidian vault on 2026-11-18 (WOR-0123), and the studio's name stays out of them as it does out of everything else here. A project's docs live in its own repo's `docs/` by default.

## Public repo: no other project names

This repo is public. Never name Philip's other projects, studios, accounts, people or private tools anywhere that gets committed: code, tests, docs, cards under `.darg/tasks`, card file names, commit messages, branch names, reports. Use the neutral stand-ins Alpha, Beta, Gamma, Delta, Project C and example-studio. The specific names to avoid are in `CLAUDE.local.md` (not committed). A name that slips in must be scrubbed from history, which means force-pushing a public repo. Before committing cards or docs, grep the staged files for those names.

## Layout

- `src/Darg.Core`: no UI. `InstanceConfig` (an instance's projects, in `%APPDATA%/Darg/<instance>/instance.json`; `DARG_INSTANCE`, `DARG_HOME`), `LastProject` (the project tab open last, its id in `last-project` beside instance.json, so the app opens to it again; kept out of instance.json so switching tabs doesn't rewrite a file people edit), `BoardStore` (boards in Tatty's markdown format, so Tatty and Obsidian see the same files), `AgentSession` (a real Claude Code session run headless over stream-json), `ChildProcesses` (everything Darg starts dies with it; `Group` ends what one process started, `Leftovers` the named heavy things an agent session left, see Memory below).
- Working files in the repo (`ProjectData` in Core, WOR-0144): what Darg writes per project (`reports/`, `mistakes/`, `artifacts/`, the project's `flows/`, `shown-boards`, and the board `tasks/` and `notes/` when Darg made them) lives in `.darg/` at the top of the project's first repo that exists here, and `.darg/` is added to `.git/info/exclude` when it is first made (a project opts in to committing it by deleting that line; it is never added again while `.darg/` exists). This repo (Darg's own) commits `.darg/tasks` (DAR-0003: force-added past the exclude, so its boards and cards travel with a clone; the rest of `.darg/` stays ignored). Boards set elsewhere (the vault's Tatty) stay. A project with no repo here keeps `<instance>/projects/<id>/`. `ReportStore.FolderFor`, `MistakeLog.PathFor`, `ArtifactStore.Folder` and `FlowStore.ProjectFolder` all go through `ProjectData.Root`, so use them, never build the path. `ProjectData.Migrate` runs first thing in `MainViewModel`'s constructor and moves the old folders in (rewriting saved agents' paths and the config's boards and notes); the footer line says what moved. Agents work in worktrees but `.darg/` is in the main checkout only: always give them absolute paths. `ProjectDetect` takes a repo's `docs/` before the vault's `Code/<name>`.
- A board per story (`StoryBoards` in Core, WOR-0087): a project's boards are its stories, with one inbox (a board named Inbox, Main or Backlog, else the first). A note's ticket lands there, and so does + Card made on it; then Haiku (`StoryBoards.Place`, after the ticket's retitle) moves it to the story board it fits, from each board's name and newest titles, its reply refused unless it is exactly one board's name; a card picked up meanwhile or held by an agent stays. The Board section shows several boards at once, a row each (⧉ Boards; `ShownBoards` keeps the pick in `<instance>/projects/<project>/shown-boards`; the tabs drag into an order, WOR-0213, kept by `BoardOrder` in `board-order` beside it, new boards at the end and the rows following it, and A–Z / Old–new sort them once, writing that order, old-new by each folder's creation time; the inbox is still the first A to Z): each further row is a `BoardViewModel` whose `Root` is the section's, which owns the filter, chips, Show completed, card panel and picks (`Root.Editor`, never a row's own); dropping a card on another row's list moves it to that board (`Drop`; list Tags are `board/listId` keys, since every board has its own c1).
- The All board and By state (WOR-0214, `CardStates` in Core, `BoardViewModel.States.cs`): the All tab (there from two boards; it leads `OverflowRow` as its `Lead`, going into the ▾ more menu once the row overflows unless it is showing) makes every board a row, as Ctrl+clicking each tab would, so moves, agents, picks, decisions and report flows work as on the rows, and the view draws one row instead (`ShownRows`: `AllRow`), its lists every board's merged by name (`CardStates.MergeColumns`) holding the rows' own tiles, each naming its board; a drop on an All list moves each card on its own board (`DropMerged`), naming any whose board lacks that list. Its lists can't be renamed, removed, minimized or bulk-started. Picking a board any other way leaves it. By state (beside the label chips; a row's header when several show) splits each list but the done column and Completed into a narrow sub-column per `CardState` its cards are in (Blocked, Ready, Agent working, Running QA, Needs you, Agent failed; `CardStates.Of`, worked out live, never stored), regrouped when a card's agent changes state (`AgentsViewModel.CardAgentChanged` → `StatesChanged`). A sub-column is a drop target for its list. A tile's top line is a `TileHead` (Views): Run QA and Work on sit beside the id while the id fits whole, else on a line of their own under it; a board name on a tile trims. On All the footer says all boards. Both are kept in the instance's `board-views` beside shown-boards (`BoardViews`: `all`, and `split <board>` lines, `*` for the All board).
- Bulk buttons (`BulkStart` in Core, WOR-0125): ▶ Work All (n) at the top of a To Do first column and the working column starts an agent on every showing card in those with none live on it (as ▶ Work on N does: together, moving them to In Progress); the backlog has ✦ Improve All (n) instead (WOR-0215, `BulkStart.Kind.Improve`), an improve agent on every showing card there under 3 stars with none on it, moving nothing; 🧪 QA Run All (n) at the top of the QA column runs QA on every card there with no QA agent. Disabled at 0; above `AskAbove` (3) the column asks "Start n agents?" inline first. A card that fails to start is named in the status line and the rest still start. The API's `work-all` / `qa-all` do the same without asking; `pwsh -File tools/bulk-start.ps1` checks it live with fake agents. Blocked cards (`BlockedStart` in Core, WOR-0173, on WOR-0172's `Blockers`): Work All and ▶ Work on N leave out a card whose Blocked by names one not yet in QA or done, its label saying so (`▶ Work All (4, 3 blocked)`) and the status line naming them; Work on one asks inline, on the tile or in the panel ("Blocked by AND-0003, In Progress. Start anyway?"), except in QA, where it only gets the work running; the API's `work-on` refuses it (and `work-all` leaves it out) unless `force: true`. A card agent's prompt lists its blockers with their columns and each one's newest report (`BlockedStart.PromptLines`). `BoardViewModel.OpenBlockers` uses the chips' kept lookup (`BlockIndex`) for counts and reads the boards again before anything starts.
- Card queues (WOR-0212; `CardQueue.cs` in Core, `QueuesViewModel`): a project has any number of named queues (`queues.json` in its `.darg/`, `QueueStore`), each worked one card at a time by `QueueRun.Next`, a pure step the app takes on every board read and every 3 s while one runs (boards read off the UI thread): it starts the next card as Work on does (`BoardViewModel.StartQueued`, on whichever board holds it, the board on screen unchanged) once the one before is done, or is in QA and a Haiku check (`QueueCheck`, run after that card's agent's turn ends; no clear answer counts as blocking) says the next doesn't need that QA passed first. A card waiting on the person (attention, or its agent asking) holds its place and the queue goes on; only a failure pauses it (the agent's turn failing, or it stopping with the card still being worked), and Resume moves on past that card. Cards with open blockers are passed over until they clear. A new queue waits for ▶ Run; + Queue (right of the label chips) fills it with the board showing's open cards, each after what it waits on, blockers on other boards pulled in (`QueueOrder`, no model); a card's menu adds it to or takes it out of each queue, with its open blockers (taking one out forgets what the queue did with it, `QueueOrder.Remove`, so added back it runs again); a tile shows `⏵ Name 3`. Each queue is a boxed lane above the board (WOR-0220, Philip's pick 2026-11-25): a queued card leaves its list (split by state or not, whatever the filter or Show completed say; `BoardViewModel.Apply` sets it aside in the row's `_lane`) and shows there as the board's own tile (`LaneTile`; a plain one that opens the card when its board isn't showing), in the queue's order, with its place, board and column, ← → ✕ (✕ puts it back in its list); folded, the lane is one line of ids. Its grip drags it among the queues (`TabDrag` with `vertical` and `grip`), its name double-clicked or ⋯ Rename renames it (`QueueStore.Rename`, unique), and ⋯ deletes it keeping its cards or with its unfinished ones (each to its board's `.deleted` folder, done ones staying). Card lookups by id go through `Tiles()` (lists and lane) so a queued card still opens. The API's `queues`, `queue-new`, `queue-add`, `queue-remove`, `queue-run` (`pause: true`), `queue-delete` (`cards: true`), `queue-rename` and `queue-move` (`to`, from 1) do the same. `CardQueueTests`, `QueueTests`.
- Ticket quality (`TicketQuality` in Core, WOR-0156): a star out of 3 beside every card's id (tile and panel), a point each for what's wanted, where and done when; red 0 to 1, amber 2 (the `Warn` theme key), green 3. It reads `Card.Sections` (everything after the description) as well as the description, leaving out How to check, QA notes, Decision and Could not reproduce, and is worked out on each read, never stored. `CardImprover.Prompt` carries the score and asks for `**Where:**` and `**Done when:**` labels, so an improved card goes green as the board reloads it.
- The Design section (WOR-0175, `DesignViewModel`, `DesignView`; design in `docs/FEATURE-PLANNING.md`): the plans in the docs folder's `design/` (`PlanStore` in Core, WOR-0174) as a tree by `parent:`, and the picked one as a page in its parts. Goals, Not doing and Design are edited in place (`PlanStore.SetSection` writes only that part); a question's option tapped writes its `**Answer:**` line (`PlanStore.Answer`); a made card's row shows its column, live agent and open blockers read from the boards each time it shows (it reloads on `Board.Reloaded` while on screen) and opens the card's panel. Plans stay current as cards land (WOR-0178, `PlanRules` in Core): a card made from a plan gets the plan's path and the rule that a choice the plan didn't settle goes into its Questions as `**Answer:** X (decided by agent, CARD, date)`; the page shows such a question with Keep (puts the person's name on it) and Change (writes the new answer and `SendBackById` the card with it as notes), the Log lists the cards' reports newest first, and `Stories.Prompt` names the plan files so a story doc links its plan. Make cards (WOR-0177, `PlanStore.MakeCards`, the API's `plan-cards {project, plan, only?, confirm?}`): each proposed row has a tick (on by default; an unticked one is kept in the plan's `unticked: ["heading", …]` property, a feature's in `unticked-features`, WOR-0199) and one button makes the ticked ones on the plan's `board:` (made with the project's columns and a 3-letter prefix from the plan's name if there is none), in Blocked by order with the new ids in their Blocked by lines, each id written into its heading, the plan set to agreed. All or nothing before anything is made: a row under 3/3 (missing parts named), an unknown or circular Blocked by, or open questions without the second press (`confirm`) make nothing; run again it makes only rows with no id and never deletes a card. Blocked by across plans (WOR-0201, `PlanScope` and `PlanMaking` in Core's `PlanRefs.cs`): an entry names a card by id, else by its heading as written, in this plan or any plan of the same project (`PlanScope.For`: the plan's whole tree from the top), `Plan title: heading` when two share it; the line is cut at commas and "and" only between things it names, so a heading holding them stays whole (`PlanCard.BlockedByText` is the line as written; `PlanCard.BlockedBy` is cut against the plan's own headings only, so read cross-plan entries through `PlanScope.BlockersOf`). `PlanMaking.Plan` says which rows can be made, in order across plans, and why each other can't (`CantMake`); the page runs it on every tick and marks each such row in full, and the button becomes "Make the N that can be made" (`skipBlocked`; the API's `ready: true`). A project plan's page has Make all under its Features (`PlanStore.MakeAll`, `DesignViewModel.MakeAll`, the API's `plan-make-all`): every ticked unmade card of its features' plans, each on its own plan's board, cross-plan blockers first, real ids in every Blocked by, one commit per plan. The Design status line wraps rather than cutting a reason off. Nothing about progress goes into the plan. Every edit the page makes is committed at once (WOR-0199, `PlanCommits` in Core; Philip's call, 2026-11-24, reversing 2026-11-20's "the page commits nothing"): an edited part, an answer, Keep, Change, a tick, Make cards' ids and Draft feature plans' links each make a `Design: <file>: <what>` commit of the plan file alone (`git commit --only`, so other changed or staged files stay as they were), in the background and in order, pushed when the project's `commits` rule for the folder is push; never leaves it uncommitted, and the status line says how it went. A planner's own turn commits per the repo's rules itself; `KeepOnly`'s put-back isn't committed. There whenever the project has a docs folder. Needs you and progress (WOR-0200): `PlanNeeds` in Core lists what in a plan waits on the person (open questions, agents' choices, made cards in the attention column with their decision or in QA); the page shows them with its planner's ask (`DesignViewModel.PlannerAsk`) as a strip above the parts, a project plan's with its feature plans' (`PlanNode.SubPlans`), each row landing on its question (lit, `PlanQuestionRow.Highlighted`), card or chat; the tree shows the count (`PlanNode.Needs`, a project's including its features'), and the header a state chip, features and cards made and done (`PlanPage.Summary`) and `PlannerText`, live from the planner. ## Agents: the protocol

`claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio`. The `--permission-prompt-tool stdio` flag is what routes permission prompts to the host as `control_request` / `can_use_tool` **and** what makes `AskUserQuestion` available at all (without it the tool is missing from print mode). A question is answered by allowing it with `answers` (question text to label) added to its input. Permissions otherwise follow the person's own Claude settings: an edit their settings allow runs without a prompt, as in the terminal. Verified on Claude Code 2.1.325, 2026-11-16.

## UI rules learned from Philip's use

- **A list must read as a list of things, not of times or cut-off text.** Chats and agents went out named "Bench · 11:00" and the first 40 characters of a prompt; it annoyed him on sight (2026-11-17). When a screenshot shows a list, check that a stranger could tell its rows apart and say what each is; generated items get a real title (`ChatTitle`).
- **Structure on disk shows as structure on screen.** A folder of docs or files is a tree that expands, not a flat list of every file (2026-11-17).
- **Drag and drop shows the thing moving** (`DragLift`), never the OS drag with nothing under the pointer.
- **Every box that sends or submits uses `views:EnterSends.Command`** (WOR-0188), never its own Enter handler: Enter sends, Shift+Enter or a typed `\` then Enter is a new line, Enter in a blank box does nothing. Editors with nothing to send (a card's description, docs, the note's paper) don't.

- **Memory (WOR-0170):** on 2026-11-20 at 05:30 the PC bluescreened (0x10E in dxgmms2, Windows' video memory manager, failing to map memory) once Windows had run out of commit: a headless emulator an agent left running was leaking, beside another agent's emulator, five worktrees' builds and test suites, and debug copies of Darg. Darg itself doesn't leak: `pwsh -File tools/perf/gpu.ps1 [-Minutes n] [-Launches n]` flips sections and cards on a throwaway instance and samples private, GPU (dedicated and shared) and committed memory; a copy stays near 130 MB of GPU and 650 MB private however long it runs or however often it's started. The copies of Darg (and its test host) and the emulators an agent starts and leaves running now end with its session (`AgentSession.LeftBehind`, by exe name, with whatever those started), and nothing else it started: a daemon its tools start for every session (claude-draw, Forge) must outlive it. `ChildProcesses.Leftovers` does it by following parent ids every 300 ms, not with a job: pwsh here is the Microsoft Store one, and what it starts goes into its package's job, not the caller's (so Darg's own job misses those too, if Darg is killed rather than closed). An emulator goes through `tools/android.ps1` only, and is stopped with `-StopEmulator` once done with.
- A freeze goes to `stalls.log` beside it (WOR-0076): a heartbeat on the UI thread (`StallWatch` in Core) logs every gap over 200 ms (`DARG_STALL_MS` to lower it) with the named sections that ran in it (`StallWatch.Shared.Section("…")`), the time in none (layout, rendering) and GC pauses. Measure there before guessing at a slowdown. `tools/perf/load.ps1` starts N cards at once on a throwaway copy of a board with fake agents (`fake_claude.py`) and prints the log. Keep off the UI thread: process starts and stdin writes (`AgentSession` queues what it sends), Haiku picks, agent saves (`AgentStore.SaveLater`), toasts; and update bound lists in place (`ListSync`) rather than rebuilding them.
