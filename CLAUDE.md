# Darg

Philip's one app for everything: per-project boards, notes, docs, code, agents, consoles and tools. Native Avalonia (C#, .NET 10), one codebase for Windows, Mac and mobile. The plan and decisions live in `docs/` (PLAN.md, the mockup, MORNING.md, PHONE-PLAN.md), which is the Docs section for this project; they moved there from the Obsidian vault on 2026-11-18 (WOR-0123), and the studio's name stays out of them as it does out of everything else here. A project's docs live in its own repo's `docs/` by default.

## Layout

- `src/Darg.Core`: no UI. `InstanceConfig` (an instance's projects, in `%APPDATA%/Darg/<instance>/instance.json`; `DARG_INSTANCE`, `DARG_HOME`), `LastProject` (the project tab open last, its id in `last-project` beside instance.json, so the app opens to it again; kept out of instance.json so switching tabs doesn't rewrite a file people edit), `BoardStore` (boards in Tatty's markdown format, so Tatty and Obsidian see the same files), `AgentSession` (a real Claude Code session run headless over stream-json), `ChildProcesses` (everything Darg starts dies with it; `Group` ends what one process started, `Leftovers` the named heavy things an agent session left, see Memory below).
- Working files in the repo (`ProjectData` in Core, WOR-0144): what Darg writes per project (`reports/`, `mistakes/`, `artifacts/`, the project's `flows/`, `shown-boards`, and the board `tasks/` and `notes/` when Darg made them) lives in `.darg/` at the top of the project's first repo that exists here, and `.darg/` is added to `.git/info/exclude` when it is first made (a project opts in to committing it by deleting that line; it is never added again while `.darg/` exists). Boards set elsewhere (the vault's Tatty) stay. A project with no repo here keeps `<instance>/projects/<id>/`. `ReportStore.FolderFor`, `MistakeLog.PathFor`, `ArtifactStore.Folder` and `FlowStore.ProjectFolder` all go through `ProjectData.Root`, so use them, never build the path. `ProjectData.Migrate` runs first thing in `MainViewModel`'s constructor and moves the old folders in (rewriting saved agents' paths and the config's boards and notes); the footer line says what moved. Agents work in worktrees but `.darg/` is in the main checkout only: always give them absolute paths. `ProjectDetect` takes a repo's `docs/` before the vault's `Code/<name>`.
- A board per story (`StoryBoards` in Core, WOR-0087): a project's boards are its stories, with one inbox (a board named Inbox, Main or Backlog, else the first). A note's ticket lands there, and so does + Card made on it; then Haiku (`StoryBoards.Place`, after the ticket's retitle) moves it to the story board it fits, from each board's name and newest titles, its reply refused unless it is exactly one board's name; a card picked up meanwhile or held by an agent stays. The Board section shows several boards at once, a row each (⧉ Boards; `ShownBoards` keeps the pick in `<instance>/projects/<project>/shown-boards`): each further row is a `BoardViewModel` whose `Root` is the section's, which owns the filter, chips, Show completed, card panel and picks (`Root.Editor`, never a row's own); dropping a card on another row's list moves it to that board (`Drop`; list Tags are `board/listId` keys, since every board has its own c1).
- Bulk buttons (`BulkStart` in Core, WOR-0125): ▶ Work All (n) at the top of the backlog, a To Do first column and the working column starts an agent on every showing card in those with none live on it (as ▶ Work on N does: together, backlog cards to In Progress); 🧪 QA Run All (n) at the top of the QA column runs QA on every card there with no QA agent. Disabled at 0; above `AskAbove` (3) the column asks "Start n agents?" inline first. A card that fails to start is named in the status line and the rest still start. The API's `work-all` / `qa-all` do the same without asking; `pwsh -File tools/bulk-start.ps1` checks it live with fake agents. Blocked cards (`BlockedStart` in Core, WOR-0173, on WOR-0172's `Blockers`): Work All and ▶ Work on N leave out a card whose Blocked by names one not yet in QA or done, its label saying so (`▶ Work All (4, 3 blocked)`) and the status line naming them; Work on one asks inline, on the tile or in the panel ("Blocked by AND-0003, In Progress. Start anyway?"), except in QA, where it only gets the work running; the API's `work-on` refuses it (and `work-all` leaves it out) unless `force: true`. A card agent's prompt lists its blockers with their columns and each one's newest report (`BlockedStart.PromptLines`). `BoardViewModel.OpenBlockers` uses the chips' kept lookup (`BlockIndex`) for counts and reads the boards again before anything starts.
- Ticket quality (`TicketQuality` in Core, WOR-0156): a star out of 3 beside every card's id (tile and panel), a point each for what's wanted, where and done when; red 0 to 1, amber 2 (the `Warn` theme key), green 3. It reads `Card.Sections` (everything after the description) as well as the description, leaving out How to check, QA notes, Decision and Could not reproduce, and is worked out on each read, never stored. `CardImprover.Prompt` carries the score and asks for `**Where:**` and `**Done when:**` labels, so an improved card goes green as the board reloads it.
- The Design section (WOR-0175, `DesignViewModel`, `DesignView`; design in `docs/FEATURE-PLANNING.md`): the plans in the docs folder's `design/` (`PlanStore` in Core, WOR-0174) as a tree by `parent:`, and the picked one as a page in its parts. Goals, Not doing and Design are edited in place (`PlanStore.SetSection` writes only that part); a question's option tapped writes its `**Answer:**` line (`PlanStore.Answer`); a made card's row shows its column, live agent and open blockers read from the boards each time it shows (it reloads on `Board.Reloaded` while on screen) and opens the card's panel. Plans stay current as cards land (WOR-0178, `PlanRules` in Core): a card made from a plan gets the plan's path and the rule that a choice the plan didn't settle goes into its Questions as `**Answer:** X (decided by agent, CARD, date)`; the page shows such a question with Keep (puts the person's name on it) and Change (writes the new answer and `SendBackById` the card with it as notes), the Log lists the cards' reports newest first, and `Stories.Prompt` names the plan files so a story doc links its plan. Make cards (WOR-0177, `PlanStore.MakeCards`, the API's `plan-cards {project, plan, only?, confirm?}`): each proposed row has a tick (on by default, kept per plan file in `DesignViewModel`) and one button makes the ticked ones on the plan's `board:` (made with the project's columns and a 3-letter prefix from the plan's name if there is none), in Blocked by order with the new ids in their Blocked by lines, each id written into its heading, the plan set to agreed. All or nothing before anything is made: a row under 3/3 (missing parts named), an unknown or circular Blocked by, or open questions without the second press (`confirm`) make nothing; run again it makes only rows with no id and never deletes a card. Nothing about progress goes into the plan, and the page commits nothing: its edits are left for the next agent or Philip (his call, 2026-11-20). There whenever the project has a docs folder.
- The planner (`Planner` in Core, WOR-0176): the Design section's + Plan box (a line, feature or project) and the API's `plan` command (`{project, idea, kind?}`, phone-callable) start an agent (purpose and job kind `plan`, so a profile rule `kind: plan` picks its model) on a file Darg names first (`Planner.FileFor`, kept on the agent as `Plan`), with `Planner.Prompt`: draft every part, open calls as Questions, cards scoring 3/3 with Blocked by, no interview. The page says it's drafting and opens the plan when the turn ends. Its chat sits beside the page (`DesignViewModel.Planner`, found by `AgentsViewModel.PlannerFor`); a message with a part picked in Change is held to that part (`PlanHold`): when the turn ends `Planner.KeepOnly` puts back whatever else in the file the planner changed. What Darg writes to the plan meanwhile (an answer, Keep, an edit, Make cards' ids: every `PlanStore.Edited`, raised by its one write path) is the person's and stands, folded into the turn's baseline by `Planner.Rebase`; an outside edit (an agent's, a text editor's) can't be told from the planner's and goes back. A plan with no planner gets one (`Planner.ReviseFirst`) on the first message. Fake claude's `FAKE_PLAN` / `FAKE_REWRITE` play it in the tests.
- Whole-project plans (WOR-0179): a `kind: project` plan has Features instead of Cards. A feature's plan is the one its title links to, else one under the project with its title (`PlanStore.FeaturePlan`); its row shows that plan's status and cards done, "drafting" while a planner writes it, else a tick. Draft feature plans (`DesignViewModel.MakeFeatures`, the API's `plan-features {project, plan, only?, confirm?}`) starts a planner per ticked feature (`StartPlan(…, parent, show: false)`, so the page stays put) told to read the project plan, and links the title to the named file at once (`PlanStore.SetFeatureLink`). `PlanStore.Tree` puts a linked plan with no `parent:` under its project; a project's progress is its features' cards.
- Artifacts (`Artifacts.cs`): HTML pages agents make, kept in `<instance>/projects/<project>/artifacts/<agent id>/`, never Claude's cloud. Each project agent gets that folder (`--add-dir`) and `ArtifactStore.Briefing` (`--append-system-prompt`; no `<>"&|` in it, it goes on a command line). `ArtifactServer` serves them on `http://localhost:47817/` (any free port if taken) with a `darg.send()` bridge put into each page; a send POSTs to a URL carrying the instance's token (`artifact-token`) and arrives at the agent that made the page as a message starting "From artifact". `/file/<absolute path>` serves images only. An image review is a `*.review.json` (title, note, folder, rows of id / original / candidates) that Darg shows through its own picker (`Review.html`, embedded in Core) rather than a page the agent writes; Send replies `id: file | note` per row (`original`, or `NEEDS PASS` for no pick), so a script can take it as it comes. The Artifacts section shows them in a `NativeWebView`. WebView2 doesn't show up in `tools/shot.ps1` captures (PrintWindow); check a page through UI Automation (Chrome elements, Invoke pattern) or a screen copy.
- The Darg API (`Api.cs`, WOR-0032): commands the app registers in `ArtifactServer.Api` (`MainViewModel.Api.cs`) for what isn't a file edit: show a card, doc, section, agent or artifact; list and read cards across the project's boards with the agents on them (`cards`, `card`; `CardIndex` in Core, WOR-0140: column takes a name or qa / attention / done, agent none / live / any); list, read, start, message and close agents; work on a card; run flows and saved commands. `GET /api/<token>` lists them with their usage lines, `POST /api/<token>/<name>` with a JSON body (or query string) runs one; an `ApiError` comes back as a 400 with its message. Fettle's briefing points it there, so a command is usable once registered: give it a usage line that says what it takes.
- Phone access (`Remote.cs` in Core, AND-0002; `docs/REMOTE.md`): `RemoteServer`, a second server on port 47818 on every network (TLS with the instance's self-signed `remote-cert.pfx`, whose SHA-256 the phone pins from the pairing QR), serving only the API commands in `RemoteAccess.Commands` to a phone sending `Authorization: Bearer <token>`; anything without a good token is a 401, a command off the list a 403. Settings' Phone part (`PhoneViewModel`, `RemoteHost`) opens a pairing (an 8-character code, 10 minutes, once, 5 wrong tries) and shows it as a QR drawn by `QrCode` (Core's own encoder; `DARG_TEST_QR_PYTHON` names a Python with OpenCV for the decode test); `POST /pair` trades the code for a token, of which `remote-devices.json` keeps only the hash, read on every request so a Revoke takes effect at once. Nothing listens until a phone is paired; `"remote": false` in instance.json leaves it out. `phones`, `phone-pair` and `phone-revoke` are PC-only commands. `DARG_REMOTE_PORT` picks another port (0: any free); the integration tests set `RemoteHost.PortOverride = 0` instead, since a test clears every `DARG_` variable mid-run.
- Also in Core: `NoteStore` (the notes wall: one .md per note with Obsidian properties; its columns in `wall.json`, edited from each column's ⋯ menu and + Column, where a rename rewrites the notes' `column:` (archived ones too) and a removed column's notes go to the first column; `MakeTicket` uses `BoardStore.Create`, which names files as Tatty does, with a title and description from `TicketText` that never drop a word and a type from `CardTypes.Guess` (bugs written in prose too); the app then has Haiku retitle the card in the background (`TicketTitle`, WOR-0082: a reply that isn't one short line in the note's own words is refused, and a card renamed meanwhile is left alone; tiny Ollama models were tried and invented things); a note with a ticket shows in a Ticketed column whatever its `column:` says, and `SyncArchive`, run on every wall reload, which a board file changing also triggers, moves it to `notes/archive/` once its card is Completed and back if the card reopens), `ClaudeDraw` (the claude-draw daemon on 7331, shared by every Claude Code session: Darg only reads its `/state`, opens the canvas and starts a blank one; agents ask and collect through their own plugin tools, so ✎ Draw sends the agent a message rather than calling the daemon). `Preview` / `DevServer` (the Site section: a project's `preview` in instance.json, else the first repo whose package.json has a `dev` script; the server runs in its own job via `ChildProcesses.Group`, because a tree kill left npm's node running).
- Mistake tracking (`MistakeLog` in Core, WOR-0037): each project's log is `<instance>/projects/<project>/mistakes/mistake_log.md`, in the schema of the mistake_log.md files kept before (Beta's): `### date: title` entries with Caught by, Category and the rest. Its own folder so agents get just that folder (`--add-dir`), and that file name because the global unlogged-mistake Stop hook already counts a write to it. Every project agent's briefing tells it to log corrections there; ✗ Mistake beside ✎ Draw sends the agent a message to log its last reply (what's typed says what was wrong; nothing typed, it asks). The Mistakes section reads the log, newest first, counts categories and marks any at `GateAt` (3) red: three of a kind is the point for a gate. Workbench only reads it; agents write it.
- Finished agent reports (`ReportStore` in Core, WOR-0061): a card agent's prompt ends with `ReportStore.Rules` instead of "move the card to done": work it couldn't verify itself goes to the board's QA column (`BoardColumns.Qa`: a column named QA, review, to check or testing, never the last) with a How to check section in the card and, as its last step, a short QA report (`<yyyyMMdd-HHmm>-<card>-qa.md`, `status: qa`; then Changed, Look at, Checked, WOR-0088), and the agent stays; work it's sure of goes to done and it writes a report, as its very last step, to `<instance>/projects/<project>/reports/<yyyyMMdd-HHmm>-<card>.md` (properties card, title, agent, commits, repo, date, read; then Asked, Done, Left). Every project agent gets that folder with `--add-dir`; a card agent is told its own id. The Reports section lists them newest first with unread ones dotted and counted on the rail; opening one sets `read: true` in the file. `AgentsViewModel.Reported` forgets the agent that wrote one once its turn ends well (one that failed or asks stays), but never for a QA report, which the list marks "to check"; a finished task goes anyway (WOR-0183, Philip 2026-11-22): a work, rework, QA or Improve card agent leaves the list once its turn ends well (`AgentsViewModel.TaskOver`, run on every state change and board read, and by Clear finished) unless its card is in For Human Attention on any of the project's boards (`AttentionCardIds`, set before the first `RefreshCards`; while it's unset nothing goes, since a check made too early forgot every asker on each restart: its decision shows on it and it is asked for one); a forgotten agent is `Gone` and never saved again (its session's exit wrote its file back); one at work, waiting on the person or failed stays, and a newer work, rework or QA agent on a card takes older settled ones off too (`ForgetReplacedBy`); a report with no `agent:` (a flow's) stands for the agents on its card started before it was written. On a card in QA, Work on gets the work running to try (`ReportStore.CheckPrompt`, WOR-0075), and the card panel's ↩ Send back (also the `send-back` API command, WOR-0079) writes what's wrong into the card as a dated entry under `## QA notes` (`QaNotes`), moves it back to In Progress and starts a card agent whose prompt opens with `ReportStore.ReworkPreface`: build on the How to check section's work, fix the notes, replace How to check for the next round and write a fresh QA report. Darg also keeps a card's reports itself as it moves, whoever moves it (WOR-0092, WOR-0102): `ColumnWatch` in Core says which cards entered the attention, QA or done column since the last read of a board (the first read only learns, so moves made while the app was closed make nothing), and `ReportFlow` writes the decision / QA report on entering attention or QA (not while a card agent is at work on it, nor within 2 minutes of another) and, on done, archives the card's QA reports to `reports/archive/` and writes a done report (unless a non-QA card agent at work will write its own). `ReportFlowTests` covers it on real board files; `pwsh -File tools/report-flow.ps1` checks it live in the debug build with fake agents. A reworked card back in QA gets Run QA without asking (WOR-0115): an agent started by Send back, or by Work on in the needs-more-work column (`BoardColumns.Rework`), has purpose `rework`, and when its card enters QA, Darg waits for that agent's turn to end and starts a QA agent unless the card has left QA or one is already on it.
- Card dependencies (`Blockers` in Core, WOR-0172; design in `docs/FEATURE-PLANNING.md`, Blocked by): a `- **Blocked by:** AND-0003, WOR-0150` line among a card's properties (after Labels; `Card.BlockedBy`, read above the description only; `BoardStore.SetBlockedBy` writes it, no ids takes it out, a card naming itself is refused). Ids are looked up across the project's boards (`CardIndex`); a blocker clears once in its board's QA column, done or Completed. A tile shows a chip (Warn) per blocker still open, and for an id no board has or a cycle (`BlockerState.Shows`), cleared ones not; the board's lookup (`BoardViewModel.BlockIndex`, the root's) is read again after any row's reload or any board.json change, so a blocker moving on a board not showing updates the tile. The card panel edits the line (Blocked by box) and lists Blocked by and Blocks as links that open the card. The API's `cards`, `card` and `boards` carry `blockedBy` (id, found, cleared, cycle, where), `blocked` and `blocks`. Holding blocked cards back from Work All / Work on is WOR-0173's.
- Card decisions (`CardDecision` in Core, WOR-0124): a card in For Human Attention waits on a `## Decision` section below its description, shaped like an AskUserQuestion (`**Question:**`, `**Asked by:** agent <id>, date`, 2 to 4 options as `- **Label** (recommended) → done|back|stay: what it means`, `**Context:**`); the parser takes the shapes agents drift into. Agents are told the shape (`CardDecision.Rules`) wherever their prompts mention the attention column. The card panel shows it at the top, recommended first, with the description folded; a pick (or the API's `decide`) writes `**Answer:**` into the card and renames the heading `## Decision answered <date>`, settles the decision report, then runs the option's action: done, back (Send back with the question as notes), stay (nothing), or with no action the answer goes to the agent that asked if it's listed (after its turn), else a new card agent with `AnswerPreface`, and the card goes to In Progress. A card landing there with a decision notifies like an agent question (notification id `card:<id>`, which opens the card); without one, once the mover's turn ends Darg sends it `CardDecision.Nudge`, then (or with no agent) Haiku drafts one (`ParseDraft` refuses anything but the asked shape). The API's `to-attention` writes a decision and moves the card. No decision: the panel says so and keeps Approve / Send back. The open decision also shows at the end of the transcript of the agent responsible (the one in Asked by, else the card's newest; `CardDecisionItem`, WOR-0169), linked: a pick there goes through `Board.Decide`, and the card's being answered anywhere, or leaving the attention column, closes it there saying how; `SyncDecisions` in `MainViewModel` keeps them in step on every board read.
- Commit rules (`Commits` in Core, WOR-0039): a project's `commits` in instance.json maps a folder (a repo, or the vault its boards are in) to `push`, `commit`, `ask` or `never`; the deepest folder holding the work wins. Fettle's briefing, the board-sorting agent and card agents (and so flows) are told the rule for where they work. No rule: Fettle never commits, a card agent follows the repo's CLAUDE.md. Edited in Setup as `rule folder` lines.
- A project with several repos (Site: `Site` and `Workspace`, WOR-0045): agents, consoles and card agents start in the first repo unless told otherwise, and every agent is given the project's other repos with `--add-dir` (`ProjectConfig.OtherRepos`, kept in its saved args). The Agents box and the Terminal toolbar show a repo picker when there's more than one; a card names its repo with a `repo:Workspace` label or a `Repo: Workspace` line (`ProjectConfig.RepoFor`), and its agent, worktree rules and flow stages go there. Saved commands still run from the first repo (`Cwd` can be relative or rooted). The Code and GitHub sections show every repo; Preview uses the first with a `dev` script.
- Consoles (the Terminal section): `Shells` in Core finds the shells installed here (PowerShell 7, Windows PowerShell, Git Bash, cmd, each WSL distro but Docker Desktop's; `$SHELL` and `/etc/shells` on Mac and Linux). + Shell opens the instance's `shell` (instance.json); picking one from ▾ opens it and makes it that default. Saved commands always run in the platform's first shell (PowerShell on Windows), the one they were written for. The ▾ menu is a popup window, so `tools/shot.ps1` doesn't capture it; use a screen copy.
- The Site section's browser is `NativeWebView` (Avalonia.Controls.WebView, WebView2 on Windows). It is a native window, so nothing Avalonia draws (Fettle, popups) shows over it.
- What notifies (`Decisions` in Core, WOR-0078): an agent's question or permission ask, and the end of a turn that ran 15 minutes or more (`Decisions.LongTurn`), failed or not; nothing else (short turns, usage limits, flow endings) makes a toast or a Fettle list entry. Every agent's briefing, Fettle's too, carries `Decisions.Briefing`: questions go through AskUserQuestion, never prose.
- Phone notifications (`Push` in Core, `MainViewModel.Push.cs`, AND-0006): what makes a desktop toast also goes to the instance's ntfy topic (instance.json `push`: server, default ntfy.sh, topic, token; none means off), set in 🎨 Settings or the API's `push` / `push-test`. A card waiting on a decision carries up to 3 options as buttons (recommended first); a button makes the phone post `darg <key> <n>` to `<topic>-reply`, which Darg streams (from the last id read, in `push.json` beside instance.json, so taps made while it was closed count) and answers the card as `decide` does, once. Answering anywhere forgets the key and deletes the phone's notification by its sequence id. The phone needs only the ntfy app and internet, not a route to the PC. `tests/Darg.Core.Tests/FakeNtfy.cs` plays ntfy in both test projects.
- The GitHub section (WOR-0151, `GitHub` and `GitHubDetail` in Core, `GitHubViewModel`): laid out as Reports is, a tab per repo when there are several, then tabs per kind (Overview, Actions, Pull requests, Issues, Commits, Branches, Releases, Notifications) with a list on the left and the picked one in full on the right, so the browser isn't needed: a run's jobs and steps, GitHub's annotations (failures first) and its failed job's log cut to the lines that say why (`LogExcerpt`, whole log a click away); a PR's checks, files and conversation in order; an issue's comments; a commit's diff; a release's notes and assets; a notification opens what it's about. One GraphQL call per repo plus runs and notifications; details are read when picked and kept until Refresh. Issues, PRs and failed runs (with the log excerpt) become cards; ✓ Mark read is the one write. GitLab repos fill the tabs they have. `GH_PATH` names another gh: the integration tests' `tools/perf/fake_gh.py` (through a .cmd, so no `&` in an API path: cmd splits there).
- Desktop extras: `Notifier` (Windows toasts carrying project and agent ids; clicking opens that agent; the Desktop project targets `net10.0-windows10.0.19041.0` when built on Windows, plain `net10.0` elsewhere, and code for toasts sits under `#if WINDOWS`), `MascotViewModel` (Fettle, the corner mascot, once called Bench: one session for the instance with `--add-dir` for every project's boards, notes and repos, and a briefing on the file formats via `--append-system-prompt`). Transcript templates live in `App.axaml`'s `Application.DataTemplates`, shared by the agents view and Fettle.
- Card links (`CardLinks` in Core, WOR-0158): `[WOR-0158](card:WOR-0158)` in any markdown Darg draws (Fettle's replies, agent transcripts, docs) opens the card's panel when clicked (`MarkdownView.OpenCard`, set by `MainWindow` to `MainViewModel.OpenCardLink`: the project on screen first, then any that has it). A bare `WOR-0158` in plain text is linked too when its prefix is a board's (`IsCardPrefix`, board.json read at most every 30 s); code, other links and lower-case branch names aren't. new-card answers with a ready `link` and Fettle's briefing says to reply with it.
- Fettle from the phone (`PhoneFettle` in Core, AND-0007): the API's `fettle-say` (`{project, text, chat?, section?, card?, doc?, voice?}`), `fettle` (`{chat, from?}`), `fettle-answer` (`{chat, answers}` or `{chat, allow}`) and `fettle-chats` are for the phone app. A phone message carries the phone's own context line ("…, on his phone"), plus `PhoneFettle.Dictated` when spoken; a question comes back as entries with options to tap. `MascotViewModel.PhoneSay` keeps the phone's chat per project running (`_phone`, counted by `HeldElsewhere`) whatever the desktop shows; it lists among the desktop's chats too. `FettleRemote` is the phone's client, over any `post(name, args)`. Fake claude takes `FAKE_ASK` (asks an AskUserQuestion) and `FAKE_CARD <project>: <title>` (calls new-card) in a message.
- Flows (multi-agent, e.g. designer → engineer → QA): `FlowStore` in Core reads them from the instance's `flows/` folder, one markdown file each (`# Name`, `Max rounds: n`, a `## Role` section per stage; a stage whose brief starts `Sends back to: Role` is a checker that ends with `VERDICT: PASS|FAIL`; any stage can end with `FLOW: STOP`). The starter `designer-engineer-qa.md` is written the first time. `FlowRun` (Desktop) runs one: an agent per stage, each handed the last reply of the ones before, fully automatic. Started from a card (context menu, card panel) or the Agents view's flow picker; `DARG_FLOW=<name>` with `DARG_AGENT` runs one without clicking. A run lasts only while the app does. A project also has flows of its own in `<instance>/projects/<project>/flows/` (`FlowStore.ForProject`: shared plus its own, its own winning a name; listed as "Name · this project"). The flow generator (WOR-0077, the + beside Run flow, and the API's `new-flow`) starts an agent with `FlowGenerator.Prompt` that writes a new flow file from what's typed in the box, basic or art (Forge from the instance's tools, the project's art recipe if any, ending in an image review), for this project or shared; the Flow list reads the folders again when its turn ends.
- Flows have their own rail section (WOR-0097, `FlowsView`, bound to `AgentsViewModel`): the flow list, a task box (`FlowTask`), Run flow, + New and Edit, and the picked flow's stages. Running or generating one switches to Agents (`ShowAgents`), where the stage agents are.
- Model profiles (`ModelProfiles` in Core): `profiles.md` in the instance folder (starter written the first time; ✎ Profiles in the Agents view opens it) names profiles (`## Name`, `Model:`, `Effort:`, `Use for:`) and `## Rules` (`- kind|type|label|role|project: value -> Profile`). Every new agent (chat, card, flow stage, Fettle chat) is started with an `AgentJob`; the first matching rule picks its profile, else Haiku (`Haiku.Ask`, one-shot, also what `ChatTitle` uses) picks from the `Use for` lines, else `Otherwise:`, else the person's own settings. The session waits for the pick ("Picking a model…"), and the transcript notes which profile and why. A model or effort picked by hand meanwhile wins.
- Card branches (`CardBranch` in Core): a card's agent, in a git repo, is told to work on a new branch named for the card (`wor-0035`) in a worktree of its own and fast-forward it in when done, alone or alongside others, unless the card names an existing branch to carry on (a `Branch: name` line or "continue on branch name" in its description, or a `branch:name` label): then it works there and doesn't merge it.
- Home (WOR-0054): every project opens to its Home section (`HomeViewModel`): the README (`ProjectHome.Readme` in Core: the first repo's, then the other repos', then the docs folder's README or index.md) drawn by `MarkdownView` with its pictures (`MdImages`: markdown images, linked badges and HTML `<img>` with its width and `align="center"`; relative paths from `BaseFolder`, which Docs sets to the open doc's folder too; SVG and web pictures show as links), and tiles above it: cards in the board's middle columns, agents working or needing you (refreshed every 3 s while shown), the newest artifacts and the last commits (`Repo.Log`). ✎ Edit opens the README in Docs; with none, an agent can draft one.
- Themes (WOR-0064): `Themes` in Core holds Dark, Light and Girlypop, each a colour for every key in `Themes.Keys` (Bg, Panel, Accent, Ink, LabelBg…); the pick is kept in `settings.json` beside instance.json (`AppSettings`). `ThemeManager` (Desktop) puts them in the app's resources as brushes, so **views take colours with `{DynamicResource Key}`, never a hex or StaticResource** (a new colour gets a key in all three themes; a test checks they match). Code-built views read `ThemeManager.Brush(key)` and rebuild on `ThemeManager.Changed` (MarkdownView, CodeView's TextMate theme). Fixed surfaces keep their own colours: post-it paper and ink, Fettle, the terminal. Fluent's palette takes only Light/Dark keys and only a change of `Accent` reaches the controls live, so a theme can set Fluent's accent (`FluentAccent`) and nothing else of Fluent's. Opened from the header's 🎨 Settings; the API's `theme` command switches too.
- Usage bar (WOR-0069): every agent turn's `rate_limit_event` carries `unifiedWindows` (five_hour and seven_day: utilization 0 to 1, resetsAt, status; seen on Claude Code 2.1.326). `StreamParser` reads them into `UsageLimited.Windows`, `AgentSession` reports each to `UsageMeter.Shared`, which keeps the latest in `usage.json` beside instance.json, and the header (`UsageViewModel`) shows the 5-hour window as a bar with a countdown to its reset and the week beside it, red from 80%, faded when the reading is over an hour old. Only Darg's own agents feed it: use in a terminal shows after Darg's next turn. Beside it, 🍃 Optimise tokens (`TokenSaver` in Core, WOR-0159; `optimiseTokens` in settings.json, the API's `optimise-tokens`): while on, every agent runs one model down (Fable→Opus→Sonnet→Haiku) at no more than medium effort, running ones from their next turn with a transcript line; what the agent was given stays as it was, so off puts it back; a model or effort picked by hand on an agent is left alone. Left of it, `today 3h 12m` (`WorkTimer`): Claude time today (from 04:00) read from claude-code-timer's per-session timings in `~/.claude/stats/timings` (its `timer-config.json` folder and break threshold), which every session's hooks write, Darg's agents and Haiku picks included: turns merged across sessions so parallel ones count once, plus gaps under the break threshold; a turn with no stop counts up to 2 h. Hidden when the timer isn't installed.
- `src/Darg.Desktop`: the Avalonia app. MVVM with CommunityToolkit.Mvvm; views in `Views/`, view models in `ViewModels/`. Every project's view stays alive across tab switches, so agents and terminals keep running.
- The phone app (AND-0003, approach in `docs/ANDROID.md`): `src/Darg.Mobile` (plain net10.0: views, view models, `DargClient` over the Darg API, `Connection`/`ConnectionStore`) and `src/Darg.Android` (the `net10.0-android` head, app id `uk.co.philipwilson.darg`). Darg.Mobile is in Darg.sln and driven headless against the real desktop API by `MobileShellTests`; Darg.Android is **not** in the sln, because the system dotnet has no android workload (installing one needs admin): `pwsh -File tools/android-setup.ps1 [-Emulator]` puts a dotnet with the workload, an Android SDK and a `darg` AVD under `D:\Android` (`DARG_ANDROID_ROOT`), and `pwsh -File tools/android.ps1 [-Emulator] [-NoBuild]` builds, installs over adb, runs `adb reverse tcp:47817` so the phone's localhost is the desktop, writes the instance's token into the app (run-as, debug builds) and starts it. With `-Emulator` it never starts a second emulator (it waits for the one running) and stops one that hasn't booted in 5 minutes; `-StopEmulator` stops it, which an agent does when done with it (WOR-0170). Views use the Core theme keys as the desktop does; phone screens are new, not desktop views squeezed down.
- `tests/Darg.Core.Tests`: xunit, unit tests of Core. `DARG_LIVE=1` also runs the live agent test (a Haiku turn through the real CLI). A test's board goes in a folder of its own inside its temp folder, never straight in `%TEMP%`: `BoardStore.Create` numbers past every board beside it, and a stray one there failed a test for a week (WOR-0127).
- `tests/Darg.Desktop.Tests` (WOR-0127): integration tests, xunit v3 with Avalonia.Headless. The real `MainWindow`, drawn with Skia, on a throwaway instance per test (`DargApp`: one project "Proj" with a git repo, docs and a Main board in the real columns), agents played by `tools/perf/fake_claude.py` and gh by `tools/perf/fake_gh.py` (`Sandbox` sets `CLAUDE_PATH` and `GH_PATH`, short turns, and `FAKE_LOG` so `app.ClaudeCalls()` / `app.Prompts()` show what each agent was started with and sent). Toasts go to `Sandbox.Notifications` (`Notifier.Capture`), not the OS. Wait with `app.Until(condition, "what")`: a timeout prints each agent's state and last transcript lines, what fake claude was sent, and crash.log, so a failure reads without a rerun. Each test leaves `.shots/integration/<test>/` to look at. `[AvaloniaFact]`, not `[Fact]`.

## Agents: the protocol

`claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio`. The `--permission-prompt-tool stdio` flag is what routes permission prompts to the host as `control_request` / `can_use_tool` **and** what makes `AskUserQuestion` available at all (without it the tool is missing from print mode). A question is answered by allowing it with `answers` (question text to label) added to its input. Permissions otherwise follow the person's own Claude settings: an edit their settings allow runs without a prompt, as in the terminal. Verified on Claude Code 2.1.325, 2026-11-16.

## UI rules learned from Philip's use

- **A list must read as a list of things, not of times or cut-off text.** Chats and agents went out named "Bench · 11:00" and the first 40 characters of a prompt; it annoyed him on sight (2026-11-17). When a screenshot shows a list, check that a stranger could tell its rows apart and say what each is; generated items get a real title (`ChatTitle`).
- **Structure on disk shows as structure on screen.** A folder of docs or files is a tree that expands, not a flat list of every file (2026-11-17).
- **Drag and drop shows the thing moving** (`DragLift`), never the OS drag with nothing under the pointer.

## Building and checking

- **The test suite is `pwsh -File tools/test.ps1`** (WOR-0127): builds the solution, then the unit and integration tests; about 45 s; `-Unit`, `-Integration`, `-Filter <name>` (matched against `Class.Method`, e.g. `Send_back`; a filter that runs no test fails). One run per folder at a time: a second waits for the first, saying whose it is (`.shots/test.lock`). And two runs on the whole machine at a time (`DARG_TEST_SLOTS`; slot files in `%LOCALAPPDATA%\Darg\test-slots`), each then waiting while committed memory is over 85% (`DARG_TEST_COMMIT_PCT`), since every worktree is its own folder (WOR-0170: a suite peaks near 1.6 GB). It clears inherited `DARG_*` variables (the live copy's `DARG_LIVE_*` would pull HotAvalonia into the build and make the app under test think it's the live copy), and `Sandbox` does the same and points `UserHome` (Core's one way to ~/.claude) and `CLAUDE_CONFIG_DIR` into `.shots/integration/_user`, so no test reads Philip's timings or settings. The integration tests share one Avalonia application (`AvaloniaTestIsolationLevel.PerAssembly`): the per-test rebuild raced with work left posting to the dispatcher and failed one run in six. Card and QA agents run all of it. **No failing test is "unrelated":** one was, in every QA pass for a week, while it hid a real flaw. Fix it, or name it and say whether it fails without your work. A change to behaviour the app shows (a button's effect, where the screen goes, what an agent is sent, when a QA agent starts) gets an integration test that fails without it; check a test can fail by breaking the code once. The PNGs in `.shots/integration` are how an agent sees a view without a running app (Artifacts, Preview and Terminal, with a native web view or a process of their own, aren't in the smoke test yet).
- `NUGET_PACKAGES=D:/nuget/packages` (C: is small). `dotnet build`, `dotnet test`. `dotnet test` rebuilds only Core and the tests, not the app: run `dotnet build` before launching the exe to check a change, or you're looking at the old build.
- GitHub calls go through `gh` with the project's account's token (`gh auth token --user <account>`) in `GH_TOKEN` for that call only; the active gh account is never switched. A private repo seen with the wrong account answers 404.
- See it without clicking: `DARG_SECTION=Board|Agents|Preview|Terminal` opens that section of the first project; `DARG_AGENT="prompt"` starts an agent there (in `DARG_AGENT_CWD` if set). `tools/shot.ps1 -ProcessId <pid> -Out x.png` captures only the app's window (PrintWindow, works when covered). UI Automation can press its buttons (Avalonia exposes them by name; find them among the window's Button descendants, as a `NameProperty` condition on the whole tree can miss), and `AutomationElement.FocusedElement` says what has focus. Launch it with `Start-Process -WindowStyle Normal`: from Claude's shell without it the process runs with no window at all.
- **The copy Philip uses** is published: `pwsh -File tools/publish.ps1` builds Release into `D:\Apps\Darg` (closing a copy running from there first; agents are saved after every turn) and makes Start menu and desktop shortcuts. Debug builds in `bin/` are for checking. **An agent running inside Darg can't publish:** closing the installed copy kills the agent's own host (it did, twice, 2026-11-16), so the script refuses; ask Philip to run it from a terminal, or to use the header's ⟳ menu. publish.ps1 writes `source.txt` (the repo) into the install folder; ⟳ Update builds that repo into `<install>.next` while the app runs, then a helper (`Updater`, started outside the app's job with `ChildProcesses.StartOutsideJob`) waits for the app to close, copies the build in and starts it again. A copy without `source.txt` (a debug build) can only restart.
- **A live copy** (WOR-0126, an experiment): `pwsh -File tools/live.ps1` (`-Shortcut` makes "Darg (live)" shortcuts) runs Darg under `dotnet watch` from a worktree of its own (`.claude/worktrees/live`, detached at the branch the repo is on), so agents' half-made edits never reach it. The ⟳ menu then reads "⟳ live" and offers Pull in, which moves that worktree to the branch's newest commit (`LiveCopy` in Core); dotnet watch applies C# through .NET hot reload, and `.axaml` through HotAvalonia, a package referenced only in the Debug builds live.ps1 starts (MSBuild sees `DARG_LIVE_TREE`). An edit hot reload can't take makes watch close and reopen Darg by itself, which stops agents mid-turn; Restart goes back through live.ps1, and closing Darg ends live.ps1 (it watches for watch's "Waiting for a file to change before restarting"). It refuses while the installed copy runs on the same instance. Hot reload changes code, not things already built: **wiring a view's named parts in code-behind goes in a method named `InitializeComponentState`** (called from the constructor), which HotAvalonia runs again after reloading that view's XAML; MainWindow does, other views don't yet, so a reloaded view whose code-behind wires its parts loses that wiring until a restart.
- A crash in a view goes to `crash.log` in the instance folder instead of closing the app; read it after anything odd. So does a debug copy refusing to start: at most 4 agents' copies run at once (`Copies` in Core, `DARG_MAX_COPIES`, 0 for no cap; the installed copy, with `source.txt` beside it, and the live copy never count). It exits with code 3.
- Profiling (WOR-0161, `docs/performance.md`): `perf.log` beside it gets a line a minute (`PerfLog` in Core: CPU, memory, GC, pool, UI held, every top-level section and counted event, `Watch.*` file watchers and `Api *` calls; `DARG_PERF_SECONDS`), a stall held over a second logs the UI thread's stack under its line (`UiStacks`, ClrMD snapshot; `DARG_STACK_MS`, `DARG_STACKS=0`), and `pwsh -File tools/perf/analyze.ps1 [-InstanceHome dir] [-Since time]` summarises both logs.
- **Memory (WOR-0170):** on 2026-11-20 at 05:30 the PC bluescreened (0x10E in dxgmms2, Windows' video memory manager, failing to map memory) once Windows had run out of commit: a headless emulator an agent left running was leaking, beside another agent's emulator, five worktrees' builds and test suites, and debug copies of Darg. Darg itself doesn't leak: `pwsh -File tools/perf/gpu.ps1 [-Minutes n] [-Launches n]` flips sections and cards on a throwaway instance and samples private, GPU (dedicated and shared) and committed memory; a copy stays near 130 MB of GPU and 650 MB private however long it runs or however often it's started. The copies of Darg (and its test host) and the emulators an agent starts and leaves running now end with its session (`AgentSession.LeftBehind`, by exe name, with whatever those started), and nothing else it started: a daemon its tools start for every session (claude-draw, Forge) must outlive it. `ChildProcesses.Leftovers` does it by following parent ids every 300 ms, not with a job: pwsh here is the Microsoft Store one, and what it starts goes into its package's job, not the caller's (so Darg's own job misses those too, if Darg is killed rather than closed). An emulator goes through `tools/android.ps1` only, and is stopped with `-StopEmulator` once done with.
- A freeze goes to `stalls.log` beside it (WOR-0076): a heartbeat on the UI thread (`StallWatch` in Core) logs every gap over 200 ms (`DARG_STALL_MS` to lower it) with the named sections that ran in it (`StallWatch.Shared.Section("…")`), the time in none (layout, rendering) and GC pauses. Measure there before guessing at a slowdown. `tools/perf/load.ps1` starts N cards at once on a throwaway copy of a board with fake agents (`fake_claude.py`) and prints the log. Keep off the UI thread: process starts and stdin writes (`AgentSession` queues what it sends), Haiku picks, agent saves (`AgentStore.SaveLater`), toasts; and update bound lists in place (`ListSync`) rather than rebuilding them.
- Scratch output goes in `.shots/` (ignored). For anything that writes cards or notes, point the app at a throwaway instance (`DARG_HOME=.shots/home`, with its own `instance.json` and board), never at the real vault boards.
